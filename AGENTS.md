# AGENTS.md — Stinger Engine

## Project identity

- **What**: Visual novel engine (AVG/VN) running inside Minecraft NetEase China Edition
- **Type**: MC Studio AddOn, NOT a standalone app. Can only be tested in MC Studio or in-game.
- **Namespace**: `stinger`
- **Min engine**: 1.18.0
- **Framework**: QuModLibs (embedded at `StingerEngine_B/StingerEngine/include/QuModLibs/`)

## Critical: Python 2.7

The Netease ModAPI runtime is **Python 2.7**. Code that works in Python 3 will silently break.

**Forbidden**:
- f-strings (`f"hello {name}"`)
- type hints (`def foo(x: int) -> str:`)
- `print()` as function (use it sparingly; prefer `logger` or `errorPrint`)
- `async`/`await`
- `pathlib`, `dataclasses`, `enum` (unless confirmed available)
- The walrus operator `:=`

**Required**:
- `# -*- coding: utf-8 -*-` at top of every `.py` file
- `"{}".format(var)` for string formatting
- `try: ... except NameError: ...` around `long` type checks (see `saveData.py:13-16`)

## Framework conventions

### Cross-client communication (QuModLibs RPC)

The ONLY way to communicate between client and server:

- **Server → Client**: Decorate server-side methods with `@AllowCall`. Client calls `Call("MethodName", arg1=..., arg2=...)`.
- **Client → Server**: Decorate client-side methods with `@AllowCall` (like `OnSaveResponse` in `EngineClient.py`). Server calls `Call(playerId, "MethodName", ...)`.
- Server methods that need player context: decorate with `@InjectRPCPlayerId` to auto-inject `playerId` as first arg.

### UI system

- UI classes inherit `ScreenNodeWrapper` and use `@ScreenNodeWrapper.autoRegister("UiName.ClassName")`.
- The Python module MUST be imported **before** `UiInitFinished` fires. Add imports in `EngineClient.py` bottom (see lines 237-245).
- Each UI needs a matching JSON file in `StingerEngine_R/ui/` listed in `_ui_defs.json`.
- Push screens with `clientApi.PushScreen(MOD_NAME, ui_name)` via `EngineClient._schedule_push()`.
- Use `modconfig.py` constants for UI names/paths — never hardcode strings.
- Scroll panel keys in `_ui_defs.json` should be `<ui_name>/<panel_path>`. Do NOT add lazy-load false for common target panels to avoid collapse issues.

### Chapter scripts

- Each file in `chapters/` must export `script_data` as a module-level list of command dicts.
- `chapters/main.py` is the default entry point. It currently re-exports from `demo.py`.
- Command types documented in README and `scriptInterpreter.py`.
- Condition expressions use `[and]`, `[or]`, `[not]` keywords (NOT Python `and`/`or`/`not`).

### Event system

Use QuModLibs `ListenForEvent(eventName, self, self.Handler)` — not raw ModAPI event registration.

### Singleton pattern

Client and server systems are module-level singletons (`_engine_client`, `_engine_server`). Access them via `get_engine_client()` / `get_engine_server()` helper functions.

## Save system

- 18 manual slots + 1 auto + 1 quick save
- Auto-save triggers at stable pause points (label/tap/menu). Deduplication prevents redundant saves.
- Quick save/load: F5/F9 (configurable in `modconfig.py`)
- Load validation checks schema compatibility before restoring
- Save data persisted via server ExtraData, validated server-side

## MC Studio config files

These are generated by MC Studio. Do NOT modify unless you know what you're doing:
- `studio.json` — editor metadata, namespace, EditVersion
- `.mcdev.json` — debug/launch settings (game path, world options, hot reload)
- `work.mcscfg` — workspace config
- `.mcs/` — MC Studio cache (gitignored)

## Known constraints

- **Single-player only**: second player is force-disconnected on join (`EngineServer.py:103-104`)
- Error handling is not comprehensive — wrap risky operations in try/except
- No standard build/test/lint pipeline — this is a game mod, not a traditional project
- Adding new UI requires: (1) JSON file in `StingerEngine_R/ui/`, (2) entry in `_ui_defs.json`, (3) Python class in `uiScript/`, (4) import in `EngineClient.py`
